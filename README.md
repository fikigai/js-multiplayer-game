# Lab 01 — Event Loop & Game Loop

Базовий клієнт для браузерної гри в реальному часі (Vite + Vanilla JS + Canvas 2D + Biome).

## Запуск проєкту

```bash
npm install
npm run dev
```

```bash

```

Тестове середовище: монітор **165 Гц**, браузер Chrome / Edge.

### Пояснення через Event Loop

#### 1. Блокуючий цикл у кадрі (`while` на 50 мс)

JavaScript виконується в одному потоці (single-threaded Call Stack). Поки синхронний `while` тримає стек викликів протягом 50 мс, Event Loop **не може** перейти до фази рендерингу браузера (Style → Layout → Paint → Composite) і не може обробити нові події клавіатури з Task Queue. Через це частота кадрів падає до ~20 FPS, а ввід запізнюється. Водночас акумулятор у `createLoop()` компенсує пропущений час, запускаючи `update(1/60)` по 3 рази за кадр, тому `steps/s` залишається 60.

#### 2. `setInterval(..., 16)` замість `requestAnimationFrame`

`setInterval` ставить колбеки в звичайну **Task Queue (macrotasks)** і не знає про цикл оновлення екрана (VSync). Через це:

- На 165 Гц моніторі гра штучно обмежується ~60 FPS і кадри не збігаються з оновленням матриці — виникає jitter (нерівний `frame time`).
- Якщо колбек потрапляє між двома VSync або затримується іншою задачею, інтервал «пливе».
- `requestAnimationFrame` викликається браузером безпосередньо перед фазою Paint, ідеально синхронізуючись із частотою монітора та автоматично ставлячись на паузу у фонових вкладках.

#### 3. Змінний крок `dt` замість фіксованого

Коли ми передаємо реальний `rawDeltaMs / 1000` прямо у фізику:

- Симуляція стає недетермінованою: на 60 Гц і 165 Гц інтегрування дає різні похибки округлення та різні траєкторії.
- Якщо головний потік заблокується (спайк лагу або перемикання вкладки), наступний `dt` стає величезним (наприклад, 0.5–2 с), і за один крок об'єкт «перестрибує» половину арени (тунелювання крізь колізії в майбутніх лабах).

## Lab 02 — Об'єкти, прототипи та `this`

### 1. Баг і фікс `this` при передачі `ship.fire` у слухач подій

**Що ламається наївно:**
Якщо передати метод напряму як колбек — `window.addEventListener("keydown", ship.fire)` — у JavaScript спрацьовує правило втрати контексту при виклику як «голої» функції: всередині `fire()` значення `this` стає `undefined` (у strict mode / ES-модулях) або `window`. Звернення до `this.alive`, `this.#hp` чи `this.pos` падає з `TypeError`.

**Як виправили в проєкті:**

- У `Ship.update(dt, world)` метод викликається як метод екземпляра (`this.fire(world)`), де `this` жорстко прив'язаний до конкретного корабля.
- Стан клавіш інкапсульований у замиканні `createInput()`, а `fire` приймає `world` аргументом.

**Інші способи зафіксувати `this`:**

1. **Стрілкова функція-обгортка:** `() => ship.fire(world)` — стрілкові функції не мають власного `this` і беруть його з лексичного оточення.
2. **`.bind(ship)`:** `ship.fire.bind(ship)` — створює нову функцію з постійно прив'язаним `this`.
3. **Поле-стрілка в класі:** `fire = (world) => { ... }` — прив'язується до екземпляра під час створення об'єкта (створює окрему функцію на кожен екземпляр замість методу на прототипі).

### 2. Дизайн-запис: композиція замість глибокої ієрархії класів

**Як виглядала б наївна ієрархія спадкування:**
Якби ми описували поведінки через класи, дерево швидко розрослося б і зламалося на перетині фіч:

- `Entity` → `MovableEntity` → `Projectile` → `HomingProjectile`
- `Entity` → `Obstacle` → `Asteroid` → `HomingAsteroid`
- `Entity` → `Pickup` (який не рухається, але бере участь у колізіях і може мати таймер життя).

Щойно з'являється «самонавідний астероїд» або «рухомий pickup із TTL», наслідування змушує дублювати код або плодити міксини й ромбоподібні залежності.

**Чому обрали композицію (`behaviors` + чистий `Entity`):**

- Усі сутності мають лише **один рівень наслідування** від `Entity` (`Ship extends Entity`, `Bullet extends Entity`, `Asteroid extends Entity`, `Pickup extends Entity`, `Particle extends Entity`), а `World` працює з ними уніфіковано через `Map<id, Entity>`.
- Поведінки (`createTtl`, `createHoming`) — це незалежні функції `(entity, dt, world) => void`, які підключаються у масив `entity.behaviors`.
- Той самий `createHoming` працює і на кулі (`Bullet`), і на астероїді (`Asteroid`), а `Pickup` залишається легкою сутністю без зайвих гілок у дереві класів.

### 3. Перевірка ланцюжка прототипів

Підтверджено в консолі на екземплярі `Ship`:

- `Object.getPrototypeOf(ship) === Ship.prototype` → `true`
- `Object.getPrototypeOf(Ship.prototype) === Entity.prototype` → `true`
- `Object.getPrototypeOf(Entity.prototype) === Object.prototype` → `true`
- `Object.getPrototypeOf(Object.prototype) === null` → `true`
- `Object.prototype.hasOwnProperty.call(ship, "hp")` → `false` (`#hp` — приватне поле)
- `Object.prototype.hasOwnProperty.call(ship, "pos")` → `true` (власна властивість екземпляра)
- `Object.prototype.hasOwnProperty.call(Ship.prototype, "fire")` → `true` (метод на прототипі)

## Lab 03 — Асинхронний JavaScript: Promises, `async/await` і екран завантаження

### 1. Порівняння sequential `await` vs concurrent (`Promise.all`)

- **Sequential (`for ... of` + `await`)**: ~`36.28 ms` для 6 ассетів (кожен наступний запит чекає завершення попереднього).
- **Concurrent (`Promise.all`)**: ~`27.82 ms` для 6 ассетів (усі запити стартують паралельно, загальний час визначається найповільнішим із них).

### 2. П'ять головоломок порядку задач та мікрозадач

#### Головоломка 1 (`Promise` + `setTimeout` всередині `.then`)

```js
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve()
	.then(() => {
		console.log("3");
		setTimeout(() => console.log("4"), 0);
	})
	.then(() => console.log("5"));
console.log("6");
```

- **Вивід**: `1`, `6`, `3`, `5`, `2`, `4`
- **Пояснення**: Спочатку виконується синхронний код (`1`, `6`), далі повністю спустошується черга мікрозадач (`3`, потім ланцюжковий `5`), і лише в черзі макрозадач виконуються таймери (`2`, потім `4`).

#### Головоломка 2 (`async` / `await` і мікрозадачі)

```js
async function run() {
	console.log("A");
	await Promise.resolve();
	console.log("B");
}
console.log("start");
run();
Promise.resolve().then(() => console.log("C"));
console.log("end");
```

- **Вивід**: `start`, `A`, `end`, `B`, `C`
- **Пояснення**: Продовження після `await` стає в чергу мікрозадач після завершення поточного синхронного стеку (`start`, `A`, `end`), після чого мікрозадачі виконуються у порядку постановки (`B`, потім `C`).

#### Головоломка 3 (`requestAnimationFrame` vs мікрозадачі та `setTimeout`)

```js
console.log("init");
requestAnimationFrame(() => console.log("raf"));
setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("microtask"));
console.log("sync-end");
```

- **Вивід**: `init`, `sync-end`, `microtask`, а далі `raf` і `timeout` (залежно від розкладу кадру браузера).
- **Пояснення**: Мікрозадача виконується одразу після синхронного коду (`init`, `sync-end`, `microtask`), тоді як `requestAnimationFrame` запускається у фазі оновлення кадру рендерингу, а `setTimeout` — як окрема макрозадача.

#### Головоломка 4 (`async` функція без `await` і rejection propagation)

```js
async function fail() {
	throw new Error("boom");
}
console.log("before");
fail().catch((err) => console.log("caught:", err.message));
console.log("after");
```

- **Вивід**: `before`, `after`, `caught: boom`
- **Пояснення**: `async`-функція завжди повертає Promise, а викинута помилка переводить його у стан `rejected`, чий `.catch()` обробник спрацьовує асинхронно у черзі мікрозадач після синхронних `before` і `after`.

#### Головоломка 5 (Вкладені мікрозадачі та `setTimeout(..., 0)`)

```js
setTimeout(() => console.log("T1"), 0);
Promise.resolve().then(() => {
	console.log("M1");
	Promise.resolve().then(() => console.log("M2"));
});
setTimeout(() => console.log("T2"), 0);
```

- **Вивід**: `M1`, `M2`, `T1`, `T2`
- **Пояснення**: Черга мікрозадач (включно з `M2`, запланованою всередині `M1`) очищується до кінця перед переходом до наступної макрозадачі (`T1`, `T2`).

### 3. Галерея збоїв

- **404 спрайта**: `loadImage` перехоплює помилку завантаження (`HttpError 404`) і не робить зайвих ретраїв на `4xx`; на екрані показується помилка і кнопка **Retry**, гра не падає.
- **Таймаут мережі**: для запиту кімнат (`GET /api/rooms`) використовується `AbortSignal.timeout(...)`; при перевищенні ліміту запит переривається з `TimeoutError`, а лобі показує статус помилки без падіння застосунку.
- **Abort посеред завантаження**: при виході з лобі або перезапуску завантаження викликається `abort(...)`, що зупиняє очікування і відкидає застарілі оновлення стану.
- **Битий JSON**: `fetchJson` перевіряє `res.ok` і парсить JSON; при невалідному JSON або HTML замість JSON помилка ловиться у `try/catch` та виводиться з можливістю натиснути **Retry**.
